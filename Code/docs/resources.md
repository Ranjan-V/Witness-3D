# Compute planning (analytical estimates, not benchmarks)

The CPU core uses float64 solver proposals and exact rational checks. Geometry per track is small (3 unknowns, 5 or 7 rows/view plus six box rows), but repeated LP calls and Fraction bit lengths can dominate. Start with 16 tracks, three views, q=0 and dual-support extraction. Increase only after measuring. Exhaustive <=4-row search grows as O(m^4); q-hypotheses grow as binomial(n-1,q). Exceeding a configured hypothesis cap means abstention.

For DA-V2 metric Small, 24.8M float32 parameters alone occupy about 99 MB in decimal units, excluding model buffers, activations, CUDA context and libraries. This is not a peak VRAM estimate. One 640x480 float32 depth map occupies about 1.23 MB; one uint8 RGB frame about 0.92 MB; float64 depth about 2.46 MB. Native image resolution affects adapter activations because aspect-preserving lower-bound resize may enlarge one dimension. Small batches and bounded input pixel counts matter more than weight size alone.

RTX 3050 4 GB: batch 1, one model, no training, serialized inference/cache. If memory is insufficient, reduce input resolution through a documented calibrated export or run inference on CPU; do not silently alter geometry. Host RAM 16 GB: one CPU worker, small windows, no whole-dataset map loading, <=128-track global blocks. The reference runner currently retains input-track metadata and final records in host memory; cap scene exports and run shards. It is not an unlimited streaming benchmark engine.

Kaggle T4: start batch 1, then try 2 only after measuring. Two T4 GPUs have separate memory. Use distinct processes and output/cache directories on disjoint scene/frame shards; merge evaluation records with scene identity intact. Do not use DataParallel merely to imply pooled VRAM. Feature extraction is the implemented CPU ORB baseline; learned GPU matching is an optional future adapter, not an implemented speed claim.

CPU handles constraints, LPs, exact checks, hypothesis enumeration, graph operations and metrics. GPU handles only frozen batched depth in the current implementation. PyTorch GPU time is synchronized; peak allocated GPU bytes is measured by the adapter in future execution. Optional psutil samples process RSS every 20 ms; it can miss short peaks and measures process resident memory, not all child/device allocations. Per-track Profile times exclude the initial shared before-status LP; `run_efficiency.json` additionally measures all selected inference methods including shared queries and I/O, with existing-checkpoint counts disclosed. External whole-pipeline timing is needed to include matching and depth caching as well. Global first-block solve costs are recorded once, subsequent records read a cache.

TPU v5e-8 is disabled. No XLA model or solver path is supplied. An appropriate JAX/PyTorch-XLA implementation, supported model operations, numerical comparison, data pipeline and measured benefit would be required before any TPU recommendation. Arbitrary SciPy LPs or Fraction arithmetic do not run on TPU automatically.

Configuration files document planning limits. CPU threads can be set before numerical imports through the CLI. These are application budgets, not hard OS memory/CPU quotas. Runtime, useful coverage, model adapter compatibility and peak memory all remain unmeasured.
